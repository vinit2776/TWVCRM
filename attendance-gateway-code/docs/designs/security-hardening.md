# CEO Plan: Attendance Gateway Security Hardening

## Vision

### Premise Challenge (0A)
The app's core attendance logic (`computeDayStatus()`) is correct and well
isolated. The gap is trust at the edges: the punch-ingestion API has no
authentication, several state-changing actions are exploitable via CSRF
(GET requests with no token), and sessions never expire. None of this is
hypothetical — it's exploitable today, and it undermines the entire premise
of the CRM-sync project from the prior `/office-hours` design doc: synced
data is only as trustworthy as the punches feeding it.

### Existing Code Leverage (0B)
`computeDayStatus()` (server.js) is the single source of truth for
attendance status and should not be touched by this hardening pass — it's
correct and this plan's tests exist to protect it, not replace it.
Password storage already uses scrypt with a per-user random salt and a
timing-safe comparison (`hashPassword`/`verifyPassword` in server.js) — this
is already correct and out of scope; only the *seed values* (`password123`,
`admin123`) and the lack of forced rotation are the actual gap (item 6).

### Current exposure of `/api/punch`
This endpoint is intended to be called only by the biometric device (or its
on-prem middleware) on the internal network — it is not yet exposed to the
public internet, and the physical device isn't even connected yet (per the
prior design doc). That's why authenticating it (item 1) is urgent — it
currently trusts *any* caller on the reachable network to spoof punches for
*any* employee_id — while body-size DoS protection (item 8) is lower
urgency: exploiting it requires the kind of broad network reachability the
endpoint doesn't have yet. This is not a contradiction, but item 8 becomes
urgent, not optional, the moment `/api/punch` is exposed beyond the internal
network — TODOS.md must say so explicitly.

### Dream State (12mo)
```
CURRENT STATE                    THIS PLAN                     12-MONTH IDEAL
Single-file server,       --->   Auth on punch API,      --->  Modular service,
no auth on punch API,            CSRF protection,               authenticated device
no tests, in-memory              session TTL, audit log,        ingestion, full test
sessions                          core-logic tests                coverage, CRM sync live
```

## Chosen Implementation Approach

**Approach A: Minimal hardening** (of 3 considered — B: structural rebuild,
C: framework migration). Smallest diff that closes the exploitable holes
without a framework migration or file-structure rewrite. `computeDayStatus()`
and all routing/rendering stay as-is except where a route needs to move from
GET to POST for CSRF safety.

## T3 — SameSite=Lax Verification (resolves finding #18)

**Conclusion: rely on `SameSite=Lax` + GET→POST. Do not build the full
synchronizer-token system.**

Reasoning: `SameSite=Lax` (already set on the `session` cookie) sends the
cookie on a cross-site **top-level GET navigation** (so a normal link click
still works, e.g. returning from an external redirect), but does **not**
send it on a cross-site **POST** — including an auto-submitting cross-site
`<form method="POST">`, the classic CSRF vector. Chrome's old "Lax+POST"
2-minute grace-period exception (a temporary mitigation during the
SameSite-by-default rollout circa 2020) has since been removed from modern
browsers; a cross-site POST no longer carries a Lax cookie at all.

So: converting `/leave/decide`, `/permission/decide`, `/admin/toggle-onsite`,
`/leave/apply`, `/permission/apply`, `/overtime/apply`, and `/overtime/decide`
from GET to POST closes the actual exploitable path (a forged link or
`<img>`/auto-nav GET already stops working once the route only accepts
POST), and `SameSite=Lax` closes the remaining POST-based forgery path,
without any additional token machinery.

Residual risk accepted: browsers old enough to ignore `SameSite` entirely
are a vanishingly small population for an internal, company-managed tool,
and this app has no subdomain-cohabitation exposure (single origin, single
app) where SameSite protection would be insufficient on its own. If this
app is ever deployed alongside other apps on shared subdomains, or the
threat model changes (e.g. handling higher-value data), revisit with a real
synchronizer-token implementation.

## Dream State Delta
This plan does not reach the 12-month ideal (modular service, authenticated
device ingestion, full test coverage, CRM sync live) — it closes the trust
gap at the edges of the CURRENT single-file architecture so that the CRM-sync
project (already designed, not yet built) has trustworthy data to sync in
the first place. The structural rebuild (Approach B/C) remains available as
a later step if/when the single-file architecture itself becomes the
bottleneck.
