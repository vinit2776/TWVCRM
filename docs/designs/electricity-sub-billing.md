# CEO Plan: Electricity Sub-Billing (Back-to-Back) Module
Generated by /plan-ceo-review on 2026-06-11
Branch: main | Mode: SELECTIVE EXPANSION | Approach: B (Full module)
Repo: vinit2776/TWVCRM

## Problem

At single-tenant locations, the landlord bills TWV for electricity each month:
total units split into a utility portion (rate varies monthly, set by the utility
tariff) and a generator/DG portion (rate fixed per location, e.g. ₹30/unit), at a
location-specific ratio (e.g. 90:10). TWV must re-bill the SAME total units to the
occupying customer at a DIFFERENT ratio (e.g. 80:20) with a predefined per-location
rate markup, issue a PI/tax invoice with a Razorpay payment link, and track
collection through Receivables/AR.

Today none of this exists in the CRM: no per-location electricity config, no
landlord bill capture, no computed customer invoice, no margin visibility.

## Worked Example (canonical test case)

Landlord side (90:10 split, location-specific):
- Total units: 6486
- Utility: 5837.4 units × utility rate (varies monthly, e.g. ₹8.50) = ₹49,617.90
- Generator: 648.6 units × ₹30.00 (fixed per location) = ₹19,458.00

Customer side (80:20 split, contract-specific, defaulted from location):
- Same 6486 total units (full pass-through, override allowed)
- Utility: 5188.8 units × (landlord utility rate + markup rule) — markup is ₹/unit
  or % per location config, manually overridable per bill
- Generator: 1297.2 units × customer generator rate
- GST: 18% (CGST 9% + SGST 9%, intra-state only — existing rule) on full amount
- Grand total rounded to nearest rupee with explicit round-off line

### Clarity pins (from spec review)

- **Maker/checker roles**: maker = `accounts`, `office_admin`, `floor_manager`,
  `admin`; checker = `admin`, `manager`, `accounts`. The checker must be a
  DIFFERENT user than the maker (no self-approval), enforced server-side.
- **% markup base**: a percent markup applies to the landlord's monthly utility
  rate only. The customer generator rate is an independent config value (not
  derived from the landlord DG rate).
- **Statement numbering**: electricity statements share the existing statement
  and GST-invoice numbering sequences — no new prefix/series.
- **Mid-month contract end**: full pass-through still applies; use the D5 units
  override if a split is negotiated. E1 nag fires only if a contract was active
  during any part of the bill month.
- **E4 margin formula**: margin % = (customer pre-GST subtotal − landlord bill
  total) / landlord bill total.
- **Interstate**: all electricity locations are intra-state; CGST+SGST only
  (matches the existing enforced rule — IGST never applies).

## Architecture

```

─────────────                          ─────────────
location_electricity_config            contract electricity settings

  landlord vendor_id, bill-due day)      customer DG rate, defaults from location)
        │                                      │
        ▼                                      │
[Capture landlord bill]                        │
 electricity_bills (loc + month,               │
  meter line rows, attachment)                 │
        │                                      │
        ├──────► vendor_bills (auto-created,   │
        │         linked, approval flow as     │
        │         today → Acc Payables)        │
        ▼                                      ▼
        └────────► [Compute customer invoice] ◄┘
                    units × customer split × derived rates
                    + 18% GST + rupee rounding
                          │
                          ▼
                   [Maker-checker review dialog]
                    (prior 3-month units, anomaly amber flag,
                     unit/rate overrides, margin preview)
                          │  confirm
                          ▼
                   billing_statements (type='electricity',
                    due = dispatch + 7d)
                          │
              ┌───────────┼─────────────────┐
              ▼           ▼                 ▼
        PI/GST PDF   Razorpay link    Receivables/AR
        + annexure   (existing rail)  aging + reminders
                                      (existing rail)
```

Revision flow: landlord bill revised after dispatch → void customer statement
(existing void endpoint: blocked if payments recorded; un-links charges; creates
fresh draft with back-reference) → recompute → re-review → re-dispatch.
Constraints inherited from the void endpoint (accepted for v1): void is
**admin-only** — a revision initiated by accounts/manager waits for an admin to
void (acceptable; revisions are rare). Statements whose GST invoice was issued
via Tally (`issuance_channel = 'tally'`) **cannot be voided** — post-GST
revisions require a credit note, which is out of v1 scope (documented
limitation; revise freely at PI stage only).

## Tally Integration

Electricity statements ride the same Tally rail as other statements — this is
in scope, not incidental:
- **Ledger mapping**: electricity recovery posts to a dedicated ledger via the
  existing `primary_head` / ledger-default mechanism (migration 00246 pattern).
  Add an electricity head to constants + Tally ledger defaults.
- **Auto-GST on payment**: the payment webhook auto-fires `generate-gst-invoice`
  and `enqueueTallyReceiptVoucher` on full payment. The GST invoice generator
  must therefore render electricity line items and the E3 annexure (implementation
  step 6 covers both PI and GST paths).
- **Receipt-voucher reverse-sync**: applies unchanged — no electricity-specific
  work, but verify in end-to-end testing.
- **Void guard**: see revision-flow constraints above.

Decoupling rule: customer invoice dispatch does NOT block on landlord vendor-bill
approval. The two flows share a source record but proceed independently —
vendor-bill approval gates paying the landlord, not billing the customer.

## Data Model (new)

1. `location_electricity_config` (or columns/JSONB on locations — implementer's
   call, prefer separate table for RLS clarity):
   - location_id FK, enabled, landlord_vendor_id FK→procurement_vendors,
     landlord_utility_pct + landlord_generator_pct (must sum 100),
     landlord_generator_rate, bill_due_day_of_month (for E1 nag),
     defaults for customer side: customer_utility_pct/customer_generator_pct,
     markup_type ('per_unit'|'percent'), markup_value, customer_generator_rate
2. Contract electricity settings (JSONB column `electricity_settings` on
   contracts, pre-filled from location defaults at contract creation/activation):
   - customer_utility_pct, customer_generator_pct, markup_type, markup_value,
     customer_generator_rate, gst_rate (defaults to contract tax_percentage)
3. `electricity_bills`:
   - location_id, contract_id, bill_month/year, landlord bill number + date,
     attachment path (B2), status ('draft'|'invoiced'|'revised'),
     vendor_bill_id FK (auto-created), billing_statement_id FK (after dispatch),
     totals, created_by, revised_from_id (self-FK for revision chain)
4. `electricity_bill_lines`:
   - electricity_bill_id FK, line_type ('utility'|'generator'), meter_label,
     units, rate, amount — supports multi-meter (D8)
5. Customer-side computed snapshot stored on the electricity_bill (units billed
   override, derived customer rates, override flags) so the invoice is
   reproducible even if config changes later. **Rate/config values are snapshotted
   at confirm time — invoices never recompute from live config.**

All new tables: RLS enabled, SELECT for authenticated, mutations via API routes
with role checks (existing pattern). Migrations numbered from 00252+.

## Error & Rescue Map (key paths)

| Codepath | What can go wrong | Handling | User sees |
|---|---|---|---|
| Capture bill | No location config / no active contract at location | Validation reject (Zod) | "Configure electricity settings for this location first" / "No active contract" |
| Capture bill | Duplicate location+month | Unique constraint + friendly error; offer revision flow | "Bill for May 2026 already exists — revise it instead" |
| Capture bill | Split %s don't sum to 100, negative units/rates | Zod server-side validation | Inline field errors |
| Vendor bill auto-create | procurement insert fails after electricity_bill saved | Compensate-and-retry (chosen over an SQL RPC, which would re-implement the TS vendor-bill route logic): save bill, leave vendor_bill_id null, show retry banner; E1-style check also flags bills with missing vendor bills | "Landlord bill saved; vendor bill creation failed — retry" |
| Compute | Markup derivation yields rate ≤ landlord rate (negative margin) | Warning (not block) in review dialog | Amber margin warning |
| Dispatch | Razorpay link creation fails | Statement stays draft/finalized-unsent; retry action; error toast | "Payment link failed — retry" (existing pattern) |
| Dispatch | PDF generation fails | Same — no partial dispatch | Error toast |
| Webhook payment | payment_link.paid for electricity statement | Existing webhook handles billing_statements generically — verify statement type doesn't break the lookup | Transparent |
| Void/revise | Payments already recorded on statement | Existing void guard blocks; manual credit-note path outside v1 | "Cannot void — payments recorded" |
| Cron nag (E1) | Config exists, contract ended mid-month | Nag only when an ACTIVE contract exists for the location-month | — |
| Anomaly flag (E2) | <3 months history | Show whatever exists; no flag with zero history | "No prior data" note |

All mutations call logAudit() (fire-and-forget, existing rule). Unit/rate
overrides specifically logged with before/after values.

## Outside-Voice Amendments (adversarial review, 2026-06-11 — all user-approved)

Tension decisions (T1–T4):
- **T1 — Scope held**: full Approach B confirmed despite low invoice volume;
  build cost is low and guards protect customer-facing money demands.
- **T2 — Multi-meter rate rule**: customer utility rate = markup applied to the
  weighted-average landlord utility rate (Σ utility amounts ÷ Σ utility units).
  One utility line on the invoice; annexure shows the per-meter inputs.
- **T3 — Revisions (supersedes F3)**: electricity statements are **PI-first for
  all contracts** in v1 (gst_direct ignored for electricity); GST issues on
  payment. The void flow is **extended, not reused**: for electricity statements
  it recomputes the draft from the revised landlord bill instead of copying old
  amounts, and repairs the electricity_bills.billing_statement_id back-link.
  Post-GST corrections still require manual credit notes (documented limit).
- **T4 — Mid-month renewal**: bill attributes to the contract active on the
  LAST day of the bill month ("latest contract wins"); D5 units override covers
  exotic splits. The "one active contract" entry check is evaluated under this
  rule, not as a hard rejection when two contracts span a renewal month.

Technical corrections (verified against code):
1. **Migration is NOT purely additive**: `billing_statements.statement_type`
   has a CHECK constraint (`00223`) limited to combined/rent/usage — the
   migration must drop/recreate it to add 'electricity'. Deployment section
   amended; still zero-downtime (metadata-only ALTER) but called out in the PR.
2. **Binary rent/usage branches**: `send-proforma.ts` (isRent else-usage logic,
   hardcoded SAC 997212), `dispatch-tally-invoice.ts` and Tally ledger routing

   recovery (confirm code with CA), electricity ledger head, correct invoice
   dating. Implementation step 6 is enlarged accordingly.
3. **Existing contracts backfill**: `electricity_settings` is read with a
   read-time fallback to location defaults (no backfill needed; settings JSONB
   only stores overrides). Module works day one for already-active contracts.
4. **Vendor-bill idempotency**: unique constraint on
   `vendor_bills.electricity_bill_id` (nullable FK column added) so
   compensate-and-retry can never double-create the payable. On revision, the
   linked vendor bill is updated if unpaid/unapproved, else flagged for manual
   adjustment.
5. **CA sign-off gate**: before first customer dispatch, GST treatment (18% on
   full pass-through) and the SAC code must be confirmed in writing by the CA.
   Cheap insurance against an uncorrectable post-Tally tax position.
6. **CI wiring**: `npm test` (vitest) added to the GitHub Actions workflow
   alongside lint + build, so the compute tests gate every push.
7. **E1 nag semantics**: `bill_due_day_of_month` is relative to the FOLLOWING
   month (landlord bills for month M arrive in M+1); nag fires for month M from
   day N of M+1 until the bill is entered.
8. **Checker liquidity (accepted)**: with one accounts person, admin/manager
   touches every monthly confirm and every void. Accepted at current volume;
   revisit roles if it becomes a bottleneck.

## User Refinements (2026-06-11, post-review)

1. **Reimbursement is a LOCATION setting, not a per-bill flag** (refined
   2026-06-11): `location_electricity_config.reimbursement_enabled`, managed in
   a new "EB / Electricity Settings" section on the location detail page. Set
   once; every captured bill inherits it — no per-bill marking.
   - Enabled → bill maps to the active contract (per T4 rule), customer invoice
     auto-computed from the contract's ratio/markup, queued for maker-checker
     review.
   - Disabled → vendor bill only: flows to Acc Payables for payment processing,
     no customer statement, no contract mapping. `electricity_bills.contract_id`
     is nullable for this case; `billing_statement_id` stays null. E1 nag and
     E4 margin report consider only reimbursement-enabled locations.
   - The capture form shows the inherited behavior as a read-only badge
     ("Reimbursable → Contract: <name>" or "Vendor bill only") so the operator
     sees the outcome without making a decision. Each bill snapshots the
     setting at capture time; flipping the location setting affects future
     bills only.
   - Rationale for location (not contract): reimbursement is a property of the
     site arrangement (single-tenant + landlord deal), which persists across
     contract renewals.
2. **Contract billing ratio drives recompute** (confirms D6): the customer-side
   split/markup on the contract recomputes the customer total from the landlord
   EB bill automatically on capture, landing in the review queue "ready for
   review" — no manual math step.
3. **Billing page UI placement** (verified against current code): rent/usage is
   a filter inside the Statements tab, not top-level tabs. Plan:

## Outside-Voice Amendments, Round 2 (post-eng-review, 2026-06-11 — all user-approved)

1. **Final-month billing (P1, supersedes part of T4)**: the contract for a bill
   is found by DATE COVERAGE of the bill month (any contract overlapping the
   month; latest if two), independent of current contract status — an expired
   or cancelled contract is still billable for its final month. The contract
   cancellation/expiry flow surfaces a "final EB bill pending" alert (for
   reimbursement-enabled locations) so settlement/deposit refund accounts for
   the last electricity invoice arriving in M+1.
2. **other_charges line type**: electricity_bill_lines gains
   line_type 'other' (label + amount, no units) for fixed/demand charges,
   FPPCA, duty, late fees. Validation: Σ all lines = landlord bill total.
   Customer re-billing computes from unit lines only (unchanged); vendor bill
   and margin use the true total.
3. **Payable-side tax**: location_electricity_config gains
   landlord_gst_applicable (+ rate) and tds_section/tds_rate; the auto-created
   vendor bill is populated from these. The CA sign-off gate covers BOTH
   directions (customer SAC/GST and landlord GST/TDS). E4 margin formula
   pinned: customer pre-GST subtotal vs landlord pre-GST cost.
4. **Statement column mapping**: electricity amounts live in the statement's
   line_items with section 'electricity'; fixed_amount = 0; subtotal/tax_amount/
   total_amount carry the computed values. All four consumers (PI PDF, GST
   invoice, Tally dispatch, AR) read these same columns — no per-consumer
   recomputation.
5. **Third rounding site**: the gst-math fix PR also migrates send-proforma.ts's
   independent CGST/SGST computation to the shared function.
6. **Revision-safe uniqueness**: the electricity_bills location+month unique
   index is partial — excludes status 'revised'/superseded rows — so the
   revision chain doesn't collide with itself.
7. **gst_rate pinned**: electricity GST is 18% per D3, NOT defaulted from
   contract tax_percentage; review dialog warns if the contract's
   tax_percentage differs.
8. **Non-reimbursable path KEPT** (user decision vs outside voice): one-stop EB
   capture and per-location consumption history justify the nullable
   contract_id, which the final-month rule (item 1) needs anyway.
