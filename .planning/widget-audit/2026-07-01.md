# Dashboard Widget Audit — 2026-07-01

## Executive Summary

28 widgets are registered across 10 user roles. **No runtime usage data exists** — the codebase has no widget view instrumentation, and neither server logs, Vercel analytics, nor audit_trail entries capture dashboard API hits. All findings below are structural (code-based).

Key headline findings:
- **3 widgets are completely dead**: `recent_activities`, `notes`, and `support_summary` are registered and have API/component code, but no role's layout includes them. They generate zero user-visible value today.
- **1 widget is a near-drop**: `financial_summary` (accounts only) is largely subsumed by `cash_aging`.
- **6 high-value data sources** exist in the DB schema with no corresponding widget (COSEC presence, TDS filing, lease due dates, prepaid burn, waiver queue, headcount).
- **Instrumentation is the critical gap**: without widget_view_logs, no future audit can be data-driven.

| `analytics_*` / `*_views` tables | None exist across all 309 migration files. |
| `/var/log/` server logs | Present but OS-level only (apt, dpkg, journal). No application access logs. |

| `cosec_analytics` migration (00194) | COSEC building-access logs — unrelated to web UI widget usage. |

**Conclusion:** Zero runtime usage data is queryable. This audit is purely structural.

## Drop Candidates

### 1. `recent_activities` — Drop
- **Evidence**: Registered in `WIDGET_REGISTRY`; data is fetched inside the root `/api/dashboard` response (`recent_activities` field); component `RecentActivitiesWidget` exists at `src/components/dashboard/widgets/recent-activities-widget.tsx`. However, `DASHBOARD_ROLE_WIDGETS` does not assign this widget to **any** role.
- **Impact of drop**: The `recent_activities` array is still fetched in `/api/dashboard/route.ts` on every dashboard load, wasting a DB query. Removing the widget frees that query.
- **Action**: Remove `recent_activities` from `WIDGET_REGISTRY`. Remove `recent_activities` from the root `/api/dashboard` response payload. Delete the widget component.

### 2. `notes` — Drop
- **Evidence**: Same pattern as `recent_activities`. The `recent_notes` query runs on every root dashboard load; `NotesWidget` component exists; widget is registered. No role renders it.
- **Action**: Remove `notes` from `WIDGET_REGISTRY`. Remove `recent_notes` query from root dashboard route. Delete `NotesWidget` component.

### 3. `support_summary` — Drop
- **Evidence**: Dedicated endpoint `/api/dashboard/support` exists (admin-only, returns open/in-progress/build-approved ticket counts). `SupportSummaryWidget` component exists. Not assigned to any role. Admin and manager roles use `sla_risk` instead, which surfaces the same data with priority bucketing and SLA breach flags — strictly more useful.
- **Action**: Remove `support_summary` from `WIDGET_REGISTRY`. Delete the endpoint and component, or consolidate any unique data into `sla_risk`.

### 4. `financial_summary` — Candidate for drop / fold
- **Evidence**: Accounts-only widget surfacing count of unpaid vendor bills and count of overdue contracts. Accounts role already has `cash_aging` (aged payables buckets, including vendor bills), `renewal_pipeline` (contract churn/overdue signals), and `revenue_pulse`. `financial_summary` adds two count numbers that are visible deeper in those widgets.
- **Action**: Verify with accounts team. If `cash_aging` covers the need, remove `financial_summary` from accounts layout and from `WIDGET_REGISTRY`. Otherwise keep but note it is structurally redundant.

## Suggested New Widgets

These gaps were identified by cross-referencing existing DB tables (from migrations) against the current widget set.

### 1. Lease Payment Calendar
- **Data**: `lease_payments`, `property_leases` tables
- **What it shows**: Upcoming rent due in the next 14 days by location; overdue lease payments (status != 'paid' and due date past).
- **Why it matters**: `rent_revenue` only shows what has been paid this month. A proactive view of what's **due** prevents missed payments on commercial leases. High financial / contractual risk if missed.
- **Suggested roles**: admin, manager, accounts
- **Complexity**: Low — data is already structured, simple date-range query.

### 2. TDS Filing Tracker
- **Data**: TDS module at `/accounting/tds`; associated DB tables
- **What it shows**: Next TDS filing deadline, count of payments awaiting challan, total TDS amount at risk of late deposit.
- **Why it matters**: TDS filings have statutory deadlines with penalties. No dashboard widget currently surfaces this compliance risk. The module exists but requires active navigation.
- **Suggested roles**: admin, accounts
- **Complexity**: Medium — needs TDS table schema confirmed and deadline calendar logic.

### 3. Live Presence (COSEC)
- **Data**: `cosec_presence` table (migration 00194, `is_inside = true`), `cosec_devices`
- **What it shows**: Real-time count of members + visitors currently inside each location. Optionally shows first-entry and last-exit times.
- **Why it matters**: Floor managers and office admins need live headcount for safety, cleaning scheduling, and capacity management. Currently requires a separate report or physical check.
- **Suggested roles**: floor_manager, office_admin, admin
- **Complexity**: Low — `cosec_presence` is already maintained by the COSEC event cron. Simple SELECT WHERE is_inside = true, GROUP BY device_id.

### 4. Prepaid Credit Burn Alert
- **Data**: `prepaid_packages`, `prepaid_purchases` (migrations 00034, 00038)
- **What it shows**: Members with less than 20% of their prepaid credits remaining; expected run-out date at current burn rate.
- **Why it matters**: Members who exhaust credits mid-month get surprised at billing and are churn-prone. Proactive outreach (top-up offer) reduces churn and improves collection predictability.
- **Suggested roles**: accounts, manager, admin
- **Complexity**: Medium — requires computing burn rate from usage history.

### 5. Waiver Requests Pending
- **Data**: `waiver_requests`, `waiver_request_otps` (migrations 00089, 00090)
- **What it shows**: Count of pending waiver requests awaiting admin approval; oldest pending age.
- **Why it matters**: Waivers block invoice finalization if not actioned. Currently, the only way to see the queue is to navigate to the specific module. A count widget with drill-through prevents approval delays.
- **Suggested roles**: admin
- **Complexity**: Very low — single count query on `waiver_requests WHERE status = 'pending'`.

### 6. Headcount Compliance
- **Data**: `headcount` table (migration 00100); cron sends reminders 3×/day on weekdays
- **What it shows**: Today's confirmed headcount vs. contracted seat count per location; locations with missing headcount submissions.
- **Why it matters**: The system already sends cron reminders, but staff must submit a count. A widget showing compliance (submitted vs. missing) would replace the need for the 3×/day email nag and give management real-time visibility.
- **Suggested roles**: floor_manager, office_admin, admin
- **Complexity**: Low — `headcount` table likely has location_id, date, count fields.

## Instrumentation Recommendation

To enable data-driven audits, instrument widget API hits with a fire-and-forget log. Two options:

### Option A — Reuse `audit_trail` (no migration, ships today)

In each `/api/dashboard/<widget>/route.ts` GET handler, after the auth+role check, before the data queries:

```ts
// Fire-and-forget widget view log — never blocks the response
void supabase.from("audit_trail").insert({
  entity_type: "dashboard" as AuditEntityType,
  entity_id: dbUser.id,          // repurpose: store user id; widget in changes
  action: "view" as AuditAction,
  performed_by: dbUser.id,
  changes: { widget: "renewal_pipeline" }, // replace with the slug
});
```

**Query to count hits (last 30 days):**
```sql
SELECT
  changes->>'widget'  AS widget_slug,
  COUNT(*)            AS hits,
  COUNT(DISTINCT performed_by) AS unique_users
FROM audit_trail
WHERE entity_type = 'dashboard'
  AND action = 'view'
  AND created_at >= NOW() - INTERVAL '30 days'
GROUP BY widget_slug
ORDER BY hits DESC;
```

**Limitation**: `audit_trail.entity_type` is `VARCHAR(50)` constrained to `AuditEntityType`; adding `'dashboard'` requires updating the TypeScript union in `src/types/index.ts`.

### Option B — New `widget_view_logs` table (recommended for clean querying)

```sql
-- supabase/migrations/NNNNN_widget_view_logs.sql
CREATE TABLE widget_view_logs (
  id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  widget_slug TEXT        NOT NULL,
  user_id     UUID        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  user_role   TEXT        NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_wvl_widget_created ON widget_view_logs(widget_slug, created_at DESC);
CREATE INDEX idx_wvl_user_created   ON widget_view_logs(user_id, created_at DESC);

ALTER TABLE widget_view_logs ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Authenticated insert own widget log"
  ON widget_view_logs FOR INSERT TO authenticated
  WITH CHECK (user_id = (SELECT id FROM users WHERE auth_id = auth.uid()));

CREATE POLICY "Admin select all widget logs"
  ON widget_view_logs FOR SELECT TO authenticated
  USING (EXISTS (
    SELECT 1 FROM users WHERE auth_id = auth.uid() AND role = 'admin'
  ));
```

**30-day usage query (once data flows):**
```sql
SELECT
  widget_slug,
  COUNT(*)                      AS hits,
  COUNT(DISTINCT user_id)       AS unique_users,
  ROUND(COUNT(*) / 30.0, 1)    AS avg_hits_per_day
FROM widget_view_logs
WHERE created_at >= NOW() - INTERVAL '30 days'
GROUP BY widget_slug
ORDER BY hits DESC;
```

**Service call in each route handler (after auth):**
```ts
// After dbUser auth check, fire-and-forget
void adminSupabase.from("widget_view_logs").insert({
  widget_slug: "renewal_pipeline",
  user_id: dbUser.id,
  user_role: dbUser.role,
});
```
