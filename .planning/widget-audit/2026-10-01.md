# Dashboard Widget Audit — 2026-10-01

## Executive Summary

31 widgets are registered in `WIDGET_REGISTRY`. **4 are orphaned** — defined in the registry but assigned to zero role dashboards — and have dedicated API routes that receive real traffic only if `fetchWidgetConfig` returns them from a stale saved preference. No server-side hit-count data exists (Vercel logs are not accessible from this environment, and no widget-level instrumentation is wired into `audit_trail`). This audit is therefore static: it uses source code to determine _structural_ exposure (which roles see which widgets) as a proxy for usage, and flags the absence of runtime telemetry as the most important action item.

**Immediate drop candidates:** `financial_summary`, `support_summary`, `recent_activities`, `notes` (all unreachable from any current role config).  
**Highest-value gaps:** no debtor-aging summary for `manager`; no consolidated "my day" view for `floor_manager`; no contract-commitment tracker on any dashboard.

## Methodology

### Data sources checked (in order)

| Source | Result |
|---|---|
| `audit_trail` table (checked via codebase — `src/lib/audit.ts`) | Tracks entity mutations and views but has no `widget_view` action type. `AuditAction` enum contains no dashboard or widget entries. |
| `analytics_*` / `*_views` tables | None found — searched all 569 migration files for these patterns. |
| Server access logs (`/var/log/`, `logs/`) | `/var/log/` contains OS and Postgres/Redis logs only. No Next.js access log file exists. |
| Vercel logs | No Vercel token or CLI access from this environment. `vercel.json` is present but not usable for log queries here. |
| Widget-level instrumentation in component code | Absent — no `logAudit`, analytics, or beacon calls in any widget component. |

**Conclusion:** zero runtime hit data is available. The analysis below derives structural exposure purely from `DASHBOARD_ROLE_WIDGETS` in `src/lib/dashboard-config.ts` and from tracing each widget's fetch behaviour in component source.

### Exposure model used

- **Dead by config:** widget in `WIDGET_REGISTRY` but in **0** role arrays → never rendered (unless a stale `app_settings`-persisted config overrides it).
- **Low exposure:** widget in **1** role array only.
- **Moderate exposure:** widget in **2–3** role arrays.
- **High exposure:** widget in **4+** role arrays.

This is a lower bound on actual usage — it does not account for session frequency or role population.

## Instrumentation Patch (recommended)

To enable runtime usage tracking, extend `AuditAction` in `src/types/index.ts` and add one call per widget component:

```typescript
// src/types/index.ts — add to AuditAction union:
| "widget_view"
```

```typescript
// Example — add to any widget component's useEffect that fires on mount:
// (Pass widgetId as entity_id so queries can group by widget name)
useEffect(() => {
  logAudit(supabase, {
    entityType: "dashboard",
    entityId: widgetId,   // e.g. "sla_risk"
    action: "widget_view",
    performedBy: userId,
  });
}, []);
```

Query after 30 days:
```sql
SELECT
  entity_id AS widget_id,
  COUNT(*)                          AS total_views,
  COUNT(DISTINCT performed_by)      AS unique_users,
  MAX(created_at)                   AS last_seen
FROM audit_trail
WHERE action = 'widget_view'
  AND created_at > NOW() - INTERVAL '30 days'
GROUP BY entity_id
ORDER BY total_views DESC;
```
