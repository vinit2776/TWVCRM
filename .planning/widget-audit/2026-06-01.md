# Dashboard Widget Audit — 2026-06-01

## Executive Summary

The TWV CRM dashboard has **27 registered widgets** across 9 user roles. **No widget-level usage data exists** in the database or server logs — the `audit_trail` table tracks entity mutations only (create/update/delete/view for records), not dashboard API hits. Without instrumentation, this audit is based on static analysis: role assignment, API endpoint coverage, code path analysis, and data-model gaps.

Three widgets (`recent_activities`, `notes`, `support_summary`) are registered in `WIDGET_REGISTRY` but assigned to **zero roles**, making them effectively dead code. Thirteen of 27 API endpoints have no logging, so true usage is unmeasurable today.

**Immediate recommendations:** (1) Drop or reassign the 3 zero-role widgets. (2) Add a lightweight `widget_view` log to the existing `audit_trail` table — a one-line insert per API hit. (3) Re-audit in 30 days with real data.

---

## Methodology

**What was checked (in order per the audit brief):**

1. `src/lib/dashboard-config.ts` — `WIDGET_REGISTRY` and `DASHBOARD_ROLE_WIDGETS` for all 9 roles.
2. `src/app/api/dashboard/*` — 23 route files mapped to widget IDs.
3. `src/components/dashboard/widgets/*.tsx` — `fetch()` calls extracted to verify endpoint wiring.
4. `audit_trail` table schema (migration `00001_initial_schema.sql`) — columns: `entity_type`, `entity_id`, `action`, `changes`, `performed_by`, `created_at`. **Action enum includes `"view"` but no widget or dashboard endpoint calls `logAudit()` with `action: "widget_view"` or similar.** Confirmed by grepping all source files for `widget_view`, `dashboard.*audit`, `action.*widget`.
5. Analytics tables — only `cosec_presence` / `access_logs` enrichment exists (migration `00194_cosec_analytics.sql`); no general-purpose analytics or page-view table.
6. Server access logs — no `logs/` directory in repo; `/var/log/nginx/` not present in container. Container is ephemeral; Vercel request logs are cloud-only and not accessible from this environment.
7. Vercel config — `vercel.json` exists (cron definitions); no log-drain or analytics tokens present.

**Conclusion:** Zero queryable usage data for dashboard widgets. All findings below are static-analysis only.

## Instrumentation Recommendation

Since no usage data exists, add a minimal `widget_view` log to every `/api/dashboard/*` route handler. The `audit_trail` table already supports it — `action` is `VARCHAR(50)` and the existing `AuditAction` type includes `"view"`.

### Required code change

**1. Add `widget_view` to `AuditAction` type** (`src/types/index.ts`, line 725):

```typescript
// Before
export type AuditAction = "create" | "update" | "delete" | "login" | "email_sent" | "direct_future_contract" | "disable" | "enable" | "cheque_signed" | "view";

// After
export type AuditAction = "create" | "update" | "delete" | "login" | "email_sent" | "direct_future_contract" | "disable" | "enable" | "cheque_signed" | "view" | "widget_view";
```

**2. Add a shared logging helper** (new function in `src/lib/audit.ts`):

```typescript
export async function logWidgetView(
  supabase: SupabaseClient,
  widgetId: string,
  userId: string,
) {
  await supabase.from("audit_trail").insert({
    entity_type: "dashboard_widget",
    entity_id: "00000000-0000-0000-0000-000000000000", // sentinel — no real entity
    action: "widget_view",
    performed_by: userId,
    changes: { widget_id: widgetId },
  });
}
```

**3. Call it in each route handler** — example for `/api/dashboard/renewals/route.ts`:

```typescript
// After auth check, before the main query
logWidgetView(supabase, "renewal_pipeline", dbUser.id); // fire-and-forget
```

**4. Query usage after 30 days** (read-only, safe for production):

```sql
SELECT
  changes->>'widget_id' AS widget_id,
  COUNT(*) AS hit_count,
  COUNT(DISTINCT performed_by) AS unique_users,
  MAX(created_at) AS last_hit
FROM audit_trail
WHERE
  entity_type = 'dashboard_widget'
  AND action = 'widget_view'
  AND created_at >= NOW() - INTERVAL '30 days'
GROUP BY 1
ORDER BY 2 DESC;
```

This approach:
- Uses the existing `audit_trail` table — no migration needed
- Respects RLS (only authenticated users can insert)
- Is fire-and-forget (same pattern as `logAudit()`)
- Costs ~1 row per dashboard load per role, per widget
